## 資料結構與標籤

- **本地確認**：資料根目錄為 `/home/tsai/projects/basketball/archive/Basketball_51 dataset`，下方八個類別資料夾皆直接放 `.mp4`，沒有其他檔案。此前沒有設定檔指定 dataset path；檢查腳本以這個已存在位置為預設。

- **本地確認**：原始標籤合計 Make = **5,410 (52.47%)**，Miss = **4,901 (47.53%)**，總數 10,311。這是清理前數量，不是可直接訓練的樣本數。
- **本地確認**：全部為 H.264/MP4，解析度 320×240。FPS 分布：23.976（7,602 支）、29.97（2,475 支）、25（234 支）。片長 6.006–6.0894 秒，中位數 6.0894 秒；標示 frame 數 145–180。對全部影片做 `ffprobe` 檢查與 `ffmpeg -xerror` 完整解碼，**未發現讀取或解碼錯誤**；沒有無效檔名。這不等於逐格目視品質驗證。
- **本地確認**：檔名例如 `ft0_v122_013807_x264.mp4`，包含類別、`v` 數字、六位數時間。共有 51 個 `v` 代碼（108–184，不連續）。本地沒有獨立的 game ID、player/ball tracking、shot annotation 或 metadata 表。
- **論文確認**：第 3.1–3.2 節描述來源為 51 場 NBA 轉播，人工記錄的是**球靠近籃框**的 HHMMSS，約置於六秒 clip 中間；檔名的時間欄代表 clip 第三秒附近的原始影片時間。它不是球離手時間，也不是精確的 frame timestamp。
- **尚未確認**：每個 `v` 代碼是否唯一對應一場真實比賽；原始比賽、播出版本與日期沒有提供，不能從本地獨立核對。`v160` 與 `v166` 含大量位元完全相同的影片，尤其不能直接視為獨立比賽。

## 異常與重複

- **本地確認**：以相同檔案大小作候選、SHA-256 驗證，找到 **29 組、58 支完全相同影片**。其中 **4 組**有相同 `v` 與時間但不同類別：`v113_003041` (`mp0`/`mp1`)、`v120_013024` (`2p0`/`2p1`)、`v121_000328` (`3p0`/`mp0`)、`v183_001444` (`2p0`/`2p1`)。三組的 Make/Miss 標籤直接矛盾。
- **本地確認**：另外 **25 組**跨 `v160` 與 `v166`，且內容完全相同；其中一組 `v160_005133` 與 `v166_005133` 被標為不同投籃種類（`mp1`/`2p1`），但同為 Make。完整清單在 JSON 摘要。
- **建議**：把三組 outcome 衝突影片的兩份檔案都隔離，待人工核標後才可能恢復；其餘完全重複影片只保留一份或保持在同一 split。`v160`/`v166` 應合併成一個 split group。再以影像近似度與時間鄰近檢查近重複 clip；SHA-256 只能找到位元相同者。
- **尚未確認**：是否有轉碼後內容相同、重播、相鄰投籃或同一事件不同剪法造成的近重複，以及原始標籤的其他錯誤。

## Release frame

**Basketball-51 沒有可直接使用的 release annotation。**

- **本地確認**：本地只有 MP4 與類別/時間檔名，沒有 release frame、shot event frame、球員/球軌跡或能可靠推導 release 的標註。
- **論文確認**：論文的人工 timestamp 指向球接近籃框，未描述提供逐片 release frame 或 tracking。論文圖示中的投籃瞬間範例也不是可機器讀取的逐片標註。
- **建議，首選**：建立人工 release 標註流程。逐支標記 `r` 為「球首次清楚與投籃者手分離的 frame」，記錄 `source_video`、`r`（零起始原始解碼 frame index）、標註者、信心、不可判定原因與複核狀態。先抽樣各類與各 FPS 測試可標註率、release 所在位置、標註者一致性；看不到球或轉播切鏡等案例標為不可用，不猜測 `r`。衝突標籤先隔離。
- **建議，輔助**：球偵測/追蹤可提供候選 release 區間，人工逐格確認；轉播畫面的小球、遮擋、動態鏡頭使全自動判定風險高。姿態/手腕運動也只能提供候選，單看手腕不等於球離手。可用簡單逐格檢視介面和多人複核處理分歧；本輪不建立自動模型。
- **尚未確認**：六秒 clip 是否都涵蓋 release，以及每支影片在 release 以前有多少有效畫面。這需要人工試標與抽樣目視，不可依第 3 秒或片長推定。

## Pre-release clip 規格草案

- **建議**：每個原始 shot 先取得可信 `r` 和 split，再擷取原始解碼時間軸中嚴格早於 `r` 的畫面。基本定義為零起始索引 `[r-N, ..., r-1]`；若 `r` 不穩定，保守留 `g=1–2` 原始 frame 空隙，改用 `[r-g-N, ..., r-g-1]`。需要 `r-g-N >= 0`，否則標記該時間窗不可用，**不要**從 release 後補 frame、循環畫面或用全片做插值。每個 frame 的實際時間/PTS 應一併記錄。
- **本地確認**：原始 FPS 有三種。固定 8/16/32 個連續 frame 在 23.976 FPS 約跨 0.33/0.67/1.33 秒；25 FPS 約 0.32/0.64/1.28 秒；29.97 FPS 約 0.27/0.53/1.07 秒。同一 N 的真實觀察時間不同。
- **建議**：實驗定義優先用**秒數**固定 release 前觀察窗，例如 0.5 秒、1.0 秒、1.5 秒，再只在此窗內時間抽樣到指定 8/16/32 frame 輸入；將窗長與取樣數作獨立設定，避免混淆「看多久」和「取多少張」。也可用原生 8/16/32 frame 作敏感度分析，報告各 FPS 實際窗長。32 frame 若不足完整 pre-release 歷史，整個 shot 對該設定排除，並公布排除比例。
- **建議**：解碼、縮放、取樣、光流或任何其他影片處理只讀允許的 pre-release 區間；不把檔名、類別、比賽時間、比分 OCR、release 估計時用到的後段影像作模型特徵。標註員可為確認 release 檢視全片，但任何由完整影片產生的追蹤/平滑/標準化特徵都不得流入模型；訓練集擬合的全域標準化參數才可用於其他 split。

## Split 與資料洩漏

- **建議**：先在 shot 層建立 manifest（檔案、標籤、`v` 代碼、時間、重複群、release、可用性），清理矛盾標籤與重複，**先 split shot，再由各 split 擷取 clip**。同一次投籃的所有視窗、增強版本與重播必須在同一 split。
- **建議**：正式評估採 game/group holdout，例如約 70/15/15 的 train/validation/test；51 個 `v` 代碼可先作分組候選，**必須將 `v160` 和 `v166` 綁在同組**，並核查其他跨 `v` 近重複。分組後依 outcome 與 shot type 檢查各 split 分布，必要時調整整組分配；固定 seed、公布 manifest 與群組清單。若無法確認 game ID，結論只可稱 `v` 代碼分組測試，不能宣稱真實跨比賽泛化。
- **本地確認**：路徑與檔名直接含 Make/Miss 類別；不得將它們作模型輸入。檔名時間不是 release，卻可能讓相鄰/同事件 clip 分散。完整原片包含球飛行、碰框、結果及可能的比分或重播，任何以全片建立的輸入都會洩漏。
- **論文確認**：論文曾使用同場比賽 clip 可同時進入 train/test 的 subject-dependent 設定；這不適合作為本研究主要的跨比賽測試依據。
- **尚未確認**：畫面中比分/轉播圖文是否在某些片段提前透露當次結果；需要在 clip 建立後抽樣檢視，尤其連續罰球、重播、剪輯和轉播切鏡情形。也需人工核查 outcome 是否對應所標的 release，而非片內後續的另一投籃。

## 尚待使用者確認

1. 是否有原始 51 場比賽資訊或額外標註表，可核對 `v` 代碼與拍攝時間。
2. 人工 release 標註的人力、允許的不可判定比例與複核規則。
3. 預定主要研究問題是否需要把 `2p`/`3p`/`ft`/`mp` 全部合併，或分投籃種類報告結果。

## 重現檢查

```bash
python3 -B scripts/inspect_dataset.py --decode --output docs/dataset_summary.json
```

腳本僅讀影片並產生 JSON，不抽取訓練 clip。`--decode` 會逐支完整解碼以找損壞；省略時只檢查容器與串流 metadata。`ffprobe`、`ffmpeg` 須在 PATH 中。
